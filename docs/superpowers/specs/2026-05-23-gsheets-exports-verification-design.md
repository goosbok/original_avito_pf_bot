## UX-смена для отчётов по юзеру и его рефералам (2026-05-23)

В ходе верификации выяснилось, что `create_orders_report(user_id)` и `create_refills_report(user_id)` исторически генерили **многовкладочную** таблицу (по вкладке на юзера и каждого его реферала). По обсуждению выбран вариант **B: одна плоская вкладка + фильтр по `username`** (UI Google Sheets из коробки фильтрует по любому столбцу заголовка).

**Что меняем:**
- В обеих функциях схлопываем цикл `for i in range(len(ids_array)):` → один проход по `orders`/`refills`, отбор по множеству `scope_ids = {user_id, *referals}`.
- На выходе — одна вкладка `Заказы` / `Оплаты` с теми же 9/5 столбцами и тем же форматированием. Столбец `username` — он же фильтр.
- В `create_refills_report` дополнительно: (а) `format_display(refill['date'])` вместо сырой ISO-строки (фикс известной регрессии); (б) `get_user_str(usr)` вместо `usr['user_name']` (так же, как в orders) — чтобы у юзеров без username показывался id.
- Приведено к стилю `create_sheet()`: `Контакты` → `Да/Нет`, `Статус` → `Размещён/Выполнен`.
- Дедуп `scope_ids` (если реферал по какой-то причине оказался дублирован в строке `referals`, не получаем двойные строки).
- `_resolve_user_scope(user_id)` вынесен как маленький хелпер — общий код для обеих функций.

**Что не меняем:**
- Хендлеры `handlers/admin_orders.py:614,635` — они оба зовут `create_*_report(user['id'])` и используют только возвращённый URL; интерфейс сохранён.
- Тексты «⚠️ Пользователь не оставил заказов!» / «⚠️ Пользователь не вносил деньги!» — гейт в хендлере, не в gsheets.
- `create_sheet()` и `create_reviews_report(orders)` — не трогаем.

**Что выпадает из чек-листа Phase A** (теперь не применимо):
- ❌ «У юзера с рефералами — несколько вкладок» — теперь всегда одна.
- ❌ «У юзера без рефералов — одна вкладка» — теперь всегда одна.
- ✅ Вместо них — пункт: «На вкладке `Заказы`/`Оплаты` через фильтр в шапке `username` можно выделить отдельно юзера и каждого его реферала».
- ✅ В `create_refills_report` колонка «Дата» теперь `dd.mm.yyyy HH:MM MSK` — баг фикстся в этой же ветке, отдельная задача больше не нужна.

## Контекст

В `utils/googlesheets.py` четыре функции выгрузки данных в Google Sheets:

| # | Функция | Триггер в админке | Что выгружает |
|---|---------|-------------------|---------------|
| 1 | `create_sheet()` | callback `gsheets` в меню заказов ([handlers/admin_orders.py:280](../../../handlers/admin_orders.py)) | Все заказы (CSV → Drive → Sheets, батчи по 1000) |
| 2 | `create_orders_report(user_id)` | magic → пользователь → `orders` ([handlers/admin_orders.py:614](../../../handlers/admin_orders.py)) | Заказы конкретного юзера + его рефералов (вкладки) |
| 3 | `create_refills_report(user_id)` | magic → пользователь → `refills` ([handlers/admin_orders.py:635](../../../handlers/admin_orders.py)) | Пополнения юзера + рефералов (вкладки) |
| 4 | `create_reviews_report(orders)` | админка отзывов ([handlers/admin_reviews.py:244](../../../handlers/admin_reviews.py)) | Список отзывов |

После недавней миграции на ISO+UTC даты ([utils/dates.py](../../../utils/dates.py), коммиты `c473c8f`, `2493d33`, `45fe2fe`) три из четырёх функций используют `format_display(...)` для конвертации даты в `dd.mm.yyyy HH:MM MSK`. Цель — убедиться, что выгрузки не сломались, форматирование применяется, и большие объёмы данных (3к+ заказов) проходят через `create_sheet()` без OOM и за разумное время.

## Цели

1. Подтвердить, что все 4 выгрузки успешно создают Google-таблицы из реального Docker-окружения (prod-worktree, контейнеры `bot` и `api` уже запущены).
2. Убедиться, что после миграции дат отображение в каждой таблице — `dd.mm.yyyy HH:MM MSK`, а не ISO-строка.
3. Прогнать `create_sheet()` на синтетической нагрузке (3000 заказов), убедиться в стабильности по памяти и времени.
4. Зафиксировать найденные регрессии отдельными задачами (НЕ чинить в рамках этой работы — это работа по верификации).

## Архитектура верификации

Верификация делится на 2 фазы:

### Фаза A — функциональная (через Telegram-админку)

Запуск каждой из 4 выгрузок реальным сценарием — нажатиями в боте. Проверка выходной таблицы глазами по чек-листу. Это покрывает полный путь: `хендлер → utils.googlesheets → Google API → ответ в чат → клик по ссылке`.

### Фаза B — нагрузочная (3к заказов на `create_sheet`)

Перед нажатием «📊 Google Sheets» в админке инжектим в БД 3000 синтетических заказов, помеченных маркером `user_name='LOAD_TEST_3K'`. Запускаем выгрузку. После проверки — чистим маркером.

## Компоненты

### B1. Скрипт инжектора — `scripts/seed_load_test_orders.py`

**Назначение:** одноразово вставить N (по умолчанию 3000) заказов в таблицу `orders` для нагрузочной проверки.

**Доставка в контейнер.** `docker-compose.yml` монтирует только `./storage` — кода в контейнере из новой ветки нет. Чтобы не пересобирать image, скрипт доставляется через `docker cp`:

```
docker cp scripts/seed_load_test_orders.py original_avito_pf_bot-bot-1:/tmp/seed.py
docker exec original_avito_pf_bot-bot-1 python /tmp/seed.py 3000
```

Подключение к БД — через `DATABASE_PATH=/app/storage/database.db` (env уже выставлен в .env), т.е. та же SQLite, с которой работает бот.

**Интерфейс:**
```
python /tmp/seed.py [COUNT] [--user-id ID]
python /tmp/seed.py --cleanup
```

**Поведение:**
- Если `--user-id` не передан → берёт первого юзера из `users` (sanity: должен существовать, FK constraint).
- Использует `utils.dates.now_iso()` для поля `date` (проверяет, что ISO-пайплайн доходит до экспортёра).
- Маркирует все строки полем `user_name='LOAD_TEST_3K'` для последующей очистки.
- Поля для разнообразия (cycle):
  - `status`: `Posted` / `Completed` / `Pending` (по модулю 3)
  - `contacts`: True / False (чередуется)
  - `price`: 100 + (i % 50) × 100 (детерминированно, без random для повторяемости)
  - `position_name`: один из `["3 дня/200ПФ", "7 дней/500ПФ", "14 дней/1000ПФ"]`
  - `links`: одна строка `https://avito.ru/test/ad_{i}` (multi-link не нужен для нагрузочного — он только раздувает кол-во строк на выходе и затрудняет интерпретацию метрик)
- Одна транзакция, `executemany`. Печатает: `[seed] inserted 3000 rows in N.NN sec`.

**Идемпотентность:** при повторном запуске просто добавит ещё N строк. Это OK — за чистоту отвечает скрипт очистки.

### B2. Скрипт очистки — встроен в тот же файл

```
python scripts/seed_load_test_orders.py --cleanup
```

Выполняет `DELETE FROM orders WHERE user_name='LOAD_TEST_3K'` и печатает кол-во удалённых строк.

## Ожидаемые риски и решения

| Риск | Митигация |
|------|-----------|
| FK constraint при инжекте (нет такого `user_id`) | Скрипт сначала проверяет наличие юзера, иначе exit 1 с понятным сообщением |
| Google API rate-limit при батч-апдейте 9 запросов на 1 файл | Не блокирующее: `create_sheet` уже использует batchUpdate; если упрёмся — фиксируем как баг для отдельной работы |
| Старый креды-файл с истёкшим сроком | Будет ясная ошибка в логе → фиксируем баг |
| Тест-юзер попал в `report_exclude` | Перед инжектом — проверка `get_report_exclude()` в скрипте: если ID юзера в списке, exit 1 |
