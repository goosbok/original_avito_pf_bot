# Устойчивость интеграции с biza API (вариант B)

**Дата:** 2026-06-29
**Статус:** дизайн утверждён, готовится план реализации
**Ветка базы:** `origin/dev`

## Контекст и проблема

28–29.06 диспетчер ушёл в петлю: biza начала отвечать ошибками (сначала 429, затем
500), а `dispatch_for_paid_orders()` каждые 5 минут заново POST-ит **все** застрявшие
`pending+auto` ссылки — без пауз, без потолка попыток, без остановки. Итог: ретрай-шторм
(~4000 неудачных добавлений за сутки, тысячи дублей на стороне biza).

Обратная связь от biza (подтверждает первопричину):
- **429 = лимит 60 запросов/мин.**
- **500 = баг на их стороне** (чинят; сообщат, когда починят).
- Требование: на 429/500 **делать паузу**, а не мгновенный повтор.
- Важная особенность (выяснено эмпирически): на 429/500 biza **всё равно создаёт задачу**,
  но `task_id` нам не возвращает → отсюда дубли. Защита от этого (дедуп) — **вне объёма**
  данной доработки (вариант C, отдельной задачей после фикса 500).

## Цели

1. Не превышать **60 отправок/мин** в biza (никакой каллер не может это нарушить).
2. На 429/500/сеть — пауза/остановка, **без мгновенного повтора**.
3. Единичный/массовый сбой biza **не превращается в шторм** (стоп-кран + cooldown).
4. Ни одна ссылка не ретраится бесконечно (**потолок попыток** → ручной режим).

## Не-цели

- Дедуп/идемпотентность для «500-но-создаёт-таск» (вариант C).
- Возврат `PF_AUTO_DISPATCH_ENABLED=true` — отдельно, после подтверждения biza о фиксе 500.

## Компоненты

### Кирпич 1 — Rate limiter 60/мин (общий)
Новый модуль `services/rate_limiter.py`: простой token-bucket с методом `acquire()`,
блокирующим вызывающего, пока не освободится слот (≤ `BIZA_MAX_PER_MIN` в минуту).
Модульный синглтон-инстанс. `pf_executor_api.submit_link()` вызывает `acquire()`
непосредственно перед POST. Так лимит соблюдается **глобально** — диспетчер, admin
«Test auto» (`force_dispatch`) и любые ручные прогоны идут через один лимитер.
Тестируемость: bucket принимает «текущее время» и ёмкость параметрами (инъекция часов
в тестах), есть `reset()`.

### Кирпич 2+3 — Backoff + стоп-кран (в диспетчере)
Новый модуль `services/circuit_breaker.py`: маленький класс `CircuitBreaker` с состоянием
(счётчик ошибок подряд, `cooldown_until`):
- `record_error()` — +1 к счётчику подряд; при достижении `BIZA_BREAKER_ERRORS` ставит
  `cooldown_until = now + BIZA_COOLDOWN_MIN`.
- `record_success()` — обнуляет счётчик.
- `allow()` — `False`, пока активен cooldown, иначе `True`.

Инстанс — модульный синглтон в `order_links_dispatcher`. Поведение прохода:
- `dispatch_for_paid_orders()`: если `not breaker.allow()` — проход не запускаем (пропуск тика).
- Внутри прохода после каждой retryable-ошибки: `breaker.record_error()`; если стоп-кран
  сработал (cooldown активен) — **прерываем текущий проход** (остальные ссылки не трогаем).
- На успехе: `breaker.record_success()`.

Состояние брейкера — in-process (один процесс держит loop). При рестарте процесса
сбрасывается — это допустимо (после рестарта проба заново, лимитер всё равно бережёт темп).

### Кирпич 4 — Потолок попыток = 2 → manual (диспетчер + БД)
- Миграция: добавить `order_links.dispatch_attempts INTEGER NOT NULL DEFAULT 0`
  (в существующий механизм `apply_phaseN_migrations()` на старте api).
- В `_dispatch_one`: при retryable-ошибке (429/500/5xx/сеть) `dispatch_attempts += 1`.
  Если `dispatch_attempts >= BIZA_MAX_ATTEMPTS` (=2) → ссылка переводится в
  `delivery_mode='manual'` (остаётся `pending`), в авто больше не участвует
  (диспетчер берёт только `delivery_mode IS NULL OR 'auto'`).
- На успехе ссылка уходит в `in_work` (счётчик неважен).

Взаимодействие 3 и 4: при реальном падении biza стоп-кран прерывает проход после
~`BIZA_BREAKER_ERRORS` ссылок, поэтому за один проход в manual утечёт лишь несколько
ссылок, а не все — массового слива в ручной режим из-за временного сбоя не будет.

## Маппинг ошибок (в `_dispatch_one`)

| Ответ biza | Класс | Действие |
|---|---|---|
| 200 success | — | `in_work` + `external_id`; `breaker.record_success()` |
| 400 | `ExecutorAPIRejected` | → `manual` сразу (как сейчас; **не** считается попыткой) |
| 429 / 500 / 5xx / сеть | `ExecutorAPIError` | `attempts+=1`; `record_error()`; `attempts>=2 → manual`; если cooldown — прервать проход |
| 401 / 403 / 422 | `ExecutorAPIError` | то же, что retryable (быстро триггерит стоп-кран — это конфиг/баг, дёргать biza бессмысленно) |

## Конфиг (`data/config.py`, env-override)

| Переменная | Дефолт |
|---|---|
| `BIZA_MAX_PER_MIN` | 60 |
| `BIZA_BREAKER_ERRORS` | 3 |
| `BIZA_COOLDOWN_MIN` | 30 |
| `BIZA_MAX_ATTEMPTS` | 2 |

## Тестирование (юнит, прогон в Docker)

- **rate_limiter:** не выдаёт больше ёмкости за окно; `acquire()` блокирует/распределяет; `reset()`.
- **circuit_breaker:** срабатывает после `BIZA_BREAKER_ERRORS` подряд; `allow()=False` в cooldown; `record_success()` обнуляет.
- **dispatcher:** ссылка → `manual` после `BIZA_MAX_ATTEMPTS` неудач; `in_work` на успехе; проход прерывается при сработавшем стоп-кране; `record_success` обнуляет счётчик.
- Существующие тесты диспетчера/`submit_link` не должны сломаться (лимитер в тестах замокан/сброшен, чтобы не тормозить).

## Деплой

- Работа в ветке от `origin/dev`.
- Миграция `dispatch_attempts` применяется автоматически на старте api (`apply_phaseN_migrations`).
- `PF_AUTO_DISPATCH_ENABLED` **остаётся `false`** до подтверждения biza о фиксе 500. Включаем
  авто уже с этой защитой.
