# Партнерская программа: мультиссылки, бот + сайт

**Дата:** 2026-07-18
**Статус:** утверждено

## Цель

Полноценная партнерская программа, связывающая бота и сайт: партнер создает
реферальные ссылки-кампании (со своим слагом или случайным), ведет трафик на
сайт или в бота и получает процент с каждого пополнения приведенных
пользователей. Управление и статистика — на сайте (ЛК).

## Контекст: что уже есть

- `users.ref_id` / `ref_user_name` / `referals` (CSV) — привязка реферера.
- `/start <user_id>` в боте (`handlers/main_start.py`) — атрибуция по числовому ID.
- `services/refill.py:finalize_with_referral_bonus()` — бонус **30% с первого
  пополнения** реферала (не VIP), начисляется реферу через `finalize()`.
- `services/payment_notifications.py:notify_referrer()` — TG-уведомление о бонусе.
- Кнопка «🐼 Показать реферальную ссылку» в боте (`design.py:get_ref_text`).
- На сайте: ничего (ни UI, ни API, ни кастомных ссылок).

## Решения (утверждены)

| Вопрос | Решение |
|---|---|
| Модель вознаграждения | **10% с каждого** успешного пополнения реферала, пожизненно |
| Старая логика 30%-первое | Заменяется полностью |
| Куда начисляется | Обычный баланс сервиса (`users.balance`), вывода денег нет |
| Процент | `settings.ref_percent = 10`, правится существующей админкой настроек |
| Архитектура ссылок | **Мультиссылки-кампании**: у партнера несколько ссылок с разными слагами, статистика по каждой |
| Точки входа | Ссылка из бота ведет в TG (`t.me/...?start=ref_<user_id>-<slug>`), ссылка с сайта — на сайт (`?ref=<user_id>-<slug>`); реф-код общий |
| VIP | Как сейчас: за реферала-VIP бонус не начисляется |
| Индивидуальный процент | Админ может выставить свой процент на **каждую ссылку** (по договоренности); пусто = глобальный `ref_percent` |
| Формат реф-кода | `<user_id>-<slug>` — слаг уникален только внутри пользователя; битый/чужой слаг при валидном `user_id` → атрибуция к партнеру без ссылки |

## Данные (SQLite, схема в `utils/sqlite3.py`)

```sql
CREATE TABLE IF NOT EXISTS referral_links (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL,            -- владелец-партнер (users.id)
  slug TEXT NOT NULL COLLATE NOCASE,
  clicks INTEGER NOT NULL DEFAULT 0,
  custom_percent INTEGER,              -- NULL = глобальный settings.ref_percent;
                                       -- иначе индивидуальный % (ставит админ)
  created_at TIMESTAMP NOT NULL,
  archived_at TIMESTAMP,               -- NULL = активна
  UNIQUE (user_id, slug)               -- слаг уникален внутри пользователя
);

CREATE TABLE IF NOT EXISTS referral_bonuses (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  referrer_id INTEGER NOT NULL,        -- кому начислено
  referred_user_id INTEGER NOT NULL,   -- чье пополнение
  refill_id INTEGER,                   -- refills.increment
  link_id INTEGER,                     -- referral_links.id (может быть NULL — легаси-атрибуция)
  amount INTEGER NOT NULL,             -- начислено, руб
  percent INTEGER NOT NULL,            -- снапшот ref_percent на момент начисления
  created_at TIMESTAMP NOT NULL
);

-- users: новая колонка
ALTER TABLE users ADD COLUMN ref_link_id INTEGER;  -- через какую ссылку атрибуцирован
```

- `users.ref_id` — единственный источник правды «кто реферер».
- Легаси `referals` (CSV) и `ref_user_name` не удаляются, но новый код их не
  читает и не пишет; статистика — запросами по `ref_id`.
- Миграция — по образцу существующих guard-миграций в `utils/sqlite3.py`
  (idempotent `ALTER TABLE` / `CREATE TABLE IF NOT EXISTS`).

### Реф-код и слаги

- Канонический реф-код: `<user_id>-<slug>`, например `42-youtube`. Парсинг:
  ведущие цифры до первого `-` — ID партнера, остаток — слаг.
- Слаг: 3–32 символа, `[a-z0-9_-]`, храним в lower-case, уникальность
  регистронезависимая **внутри одного пользователя** (`UNIQUE(user_id, slug)`).
  Стоп-лист не нужен: слаг никогда не встречается в коде без `user_id`.
- Случайный слаг: 8 символов base36 (`secrets`), с ретраем при коллизии
  внутри пользователя.
- Лимит: 10 активных ссылок на партнера.

## Ссылки и атрибуция

Каждая ссылка-кампания дает две формы с одним реф-кодом `<user_id>-<slug>`:

- **Сайт:** `https://<лендинг>/?ref=<user_id>-<slug>` и
  `https://<ЛК>/?ref=<user_id>-<slug>`.
- **Бот:** `https://t.me/<bot>?start=ref_<user_id>-<slug>`
  (алфавит payload Telegram `[A-Za-z0-9_-]` — совместимо, лимит 64 символа
  выдерживается: `ref_` + 10 цифр + `-` + 32 слага = 47).

Разбор кода (общая функция, используется ботом и вебом):

1. `user_id` не существует → атрибуции нет.
2. `user_id` валиден, слаг найден среди его активных ссылок →
   `ref_id = user_id`, `ref_link_id = link.id`.
3. `user_id` валиден, слаг не найден / архивный / пустой (опечатка, удаленная
   ссылка) → **атрибуция к партнеру в общем**: `ref_id = user_id`,
   `ref_link_id = NULL` (бонус по глобальному проценту).

Потоки:

1. **Бот.** `handlers/main_start.py` разбирает `ref_<user_id>-<slug>` (новый
   префикс, до существующих веток digit/magic) общей функцией разбора → если
   у юзера `ref_id IS NULL` и это не самопривязка → сетит `ref_id` (+
   `ref_link_id`, если слаг нашелся). Легаси `/start <user_id>` продолжает
   работать — это частный случай «атрибуция к партнеру без ссылки».
2. **Лендинг** (статический `web/landing/index.html`, деплой через
   `deploy.sh`). Инлайн-скрипт: читает `?ref=<user_id>-<slug>`, дописывает `ref` ко
   всем ссылкам на ЛК (localStorage между доменами лендинга и ЛК не
   шарится — проброс только через URL), шлет клик через
   `navigator.sendBeacon('https://<ЛК>/api/referral/click?code=<user_id>-<slug>')` —
   simple request без preflight, CORS-настройка не нужна (в FastAPI её
   сейчас нет).
3. **ЛК-SPA** (`web/static/app.jsx`). При загрузке читает
   `?ref=<user_id>-<slug>` → localStorage (`ref_code`, TTL 30 дней).
   При регистрации передает `ref_code` в теле запроса.
4. **Бэкенд регистрации.** `POST /api/auth/phone/verify` и email-register
   принимают опциональное `ref_code`. Атрибуция применяется **только если
   пользователь реально создан** (не найден существующий) и слаг активен и
   не принадлежит самому юзеру.

Атрибуция одноразовая: `ref_id` никогда не перезаписывается.

## Начисление бонуса

`services/refill.py:finalize_with_referral_bonus()` переписывается:

- Триггер — как сейчас: реальный переход refill `pending → succeeded`
  (`was_newly_finalized`, защита от гонок сохраняется).
- Условие: у плательщика есть `ref_id`, плательщик не VIP. Условие
  «первое пополнение» удаляется.
- Процент: `custom_percent` ссылки, через которую атрибуцирован плательщик
  (`users.ref_link_id`), если задан; иначе глобальный `settings.ref_percent`.
  Легаси-атрибуция без ссылки (`ref_link_id IS NULL`) — глобальный процент.
- `bonus = amount * percent // 100` (целые рубли, floor); при `bonus == 0`
  ничего не пишем.
- Начисление реферу: прямой `credit()` (**не** `finalize()` — текущий вызов
  `finalize()` создает реферу запись в `refills` и ломает ему собственный
  признак «первого пополнения»).
- Запись в `referral_bonuses` (с `link_id` из `users.ref_link_id` плательщика).
- Уведомления: TG (`notify_referrer`, как сейчас) + запись в web-`notifications`.

## API (новый роутер `web/routers/referral.py`)

| Endpoint | Auth | Назначение |
|---|---|---|
| `GET /api/me/referral` | JWT | Процент, ссылки со статистикой (клики, регистрации, заработано), итоги |
| `POST /api/me/referral/links` `{slug?}` | JWT | Создать ссылку; без `slug` — случайный; 409 если слаг уже есть у этого пользователя; 422 при невалидном слаге; 409 при лимите |
| `DELETE /api/me/referral/links/{id}` | JWT | Архивировать (только свою) |
| `GET /api/me/referral/bonuses?limit&offset` | JWT | История начислений |
| `POST /api/referral/click?code=<user_id>-<slug>` | публичный | +1 к `clicks` найденной ссылки (код в query — совместимо с `sendBeacon` без preflight; битый/неизвестный код — молча 200) |

Изменяемые: `POST /api/auth/phone/verify`, email-register — опциональное поле
`ref_code`.

Админские (в существующий `web/routers/admin_users.py` + новые в
`referral.py`, доступ через существующий admin-guard):

| Endpoint | Назначение |
|---|---|
| `GET /api/admin/users/{id}/referral` | Ссылки пользователя со статистикой и эффективным процентом каждой |
| `PATCH /api/admin/referral/links/{link_id}` `{custom_percent: int \| null}` | Выставить индивидуальный процент (1–100) или сбросить на глобальный (`null`); 422 вне диапазона |

`GET /api/me/referral` отдает партнеру эффективный процент по каждой ссылке —
повышенный процент виден партнеру без пояснений откуда.

## Веб-UI (React SPA)

Новая вкладка **«Партнерка»** — `web/static/components/Referral.jsx`,
маршрут в `app.jsx`, пункт в меню Cabinet:

- Блок «Как это работает»: текущий процент (из API), условия.
- Создание ссылки: поле для своего слага + кнопка «Сгенерировать случайную».
- Таблица ссылок: слаг, две формы ссылки (сайт / бот) с кнопками копирования,
  клики, регистрации, заработано; архивирование.
- История начислений (постранично).
- Проверка на mobile И desktop breakpoints (обязательное правило проекта).

Админка (`web/static/components/AdminUsers.jsx`, существующий
`AdminUserDrawer` — рядом с балансом и VIP-тумблером):

- Секция «Партнерка»: таблица ссылок пользователя — слаг, клики, регистрации,
  заработано, процент.
- Инлайн-правка процента у каждой ссылки: числовое поле (1–100), пустое
  значение = глобальный процент (показывается плейсхолдером, например «10 —
  глобальный»). Сохранение — `PATCH /api/admin/referral/links/{id}`.

## Бот

- Кнопка «🐼 Показать реферальную ссылку»: показывает
  `t.me/...?start=ref_<slug>` основной ссылки (создается лениво при первом
  запросе, слаг случайный) + текст «управлять партнеркой и смотреть
  статистику — на сайте» со ссылкой на вкладку.
- `design.py:get_ref_text` соответственно переписывается.

## Мердж аккаунтов

При `/connect`-мердже (`services/identity.py`): если у вливаемого аккаунта
есть `ref_id`, а у основного `ref_id IS NULL` — переносим `ref_id` и
`ref_link_id`.

## Ошибки и гонки

- Занятость слага — `UNIQUE` в БД; `IntegrityError` → HTTP 409 (не
  check-then-insert).
- Двойное начисление — `was_newly_finalized` (существующий механизм).
- Самопривязка — запрещена и в боте, и на вебе.
- Удаленный реферер (`ref_id` на несуществующего юзера) — бонус молча
  пропускается (как сейчас).
- Архивная ссылка: по ней не атрибуцируем новых, но статистика и уже
  приведенные рефералы сохраняются.

## Тестирование

Юнит-тесты (запуск в Docker, `docker exec`):

- Валидация слагов (длина, алфавит, стоп-лист, регистр), генерация случайных.
- Создание/архив ссылок, лимит, 409 на дубль.
- Разбор реф-кода: валидный код, несуществующий `user_id`, битый/архивный/
  пустой слаг → fallback на атрибуцию без ссылки.
- Атрибуция: бот `ref_<user_id>-<slug>`, легаси `/start <id>`, веб `ref_code`
  при регистрации, self-referral, повторная атрибуция (не перезаписывается),
  существующий юзер (не атрибуцируется).
- Бонус: 10% с каждого пополнения, floor, VIP-исключение, гонка
  (двойной finalize → один бонус), запись в `referral_bonuses`,
  бонус не создает refill реферу.
- Индивидуальный процент: бонус по `custom_percent` ссылки, сброс на
  глобальный, легаси-атрибуция без ссылки → глобальный; админ-эндпоинты
  требуют admin-прав, валидация 1–100.
- Мердж аккаунтов с переносом `ref_id`.

## Вне скоупа

- Вывод реальных денег, отдельный партнерский баланс.
- Каскадные (многоуровневые) рефералы.
- Клики-аналитика по времени/источникам, UTM.
- Отдельная страница-дашборд партнерки в админке (глобальный процент правится
  через settings; индивидуальные — из карточки пользователя в AdminUsers).
