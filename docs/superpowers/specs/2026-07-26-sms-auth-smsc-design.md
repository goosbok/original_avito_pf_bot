# SMS-авторизация: подключение реального провайдера (SMSC.ru)

**Дата:** 2026-07-26

## Проблема

SMS-OTP вход на `lk.avito-pf.com` написан целиком, но не работает: нет реальной
отправки. Кнопка «По SMS» закомментирована в UI с 2026-06-07 с пометкой
«нужен provider integration».

Что уже готово и **не трогаем**:

| Слой | Файл | Состояние |
|---|---|---|
| API | `web/routers/auth_phone.py` | `/api/auth/phone/request-code`, `/verify`; TTL 5 мин, кулдаун 60 сек, JWT, реф-атрибуция |
| OTP | `services/otp.py` | `channel='sms'`, хеш кода с pepper, `MAX_ATTEMPTS=3` |
| Фронт | `web/static/components/PhoneLogin.jsx` | двухшаговая форма phone → code |
| Абстракция | `services/sms.py` | `SmsGateway` Protocol + `StubSmsGateway` |

Незакрыто ровно одно звено: реализация `SmsGateway`, отправляющая настоящие SMS.

## Выбор провайдера

**SMSC.ru.**

Telegram Gateway и MAX отвергнуты явным решением: вход нужен именно по SMS.
Отдельно отмечено, что Telegram Gateway и не решал бы задачу — Telegram-OTP
(`web/routers/auth_telegram.py`) уже покрывает аудиторию с Telegram, а SMS нужен
ради тех, у кого его нет.

Почему SMSC, а не SMS Aero: интеграция — один HTTP-запрос без SDK, что под
существующий `Protocol` с единственным методом `send_code(phone, code)` ложится
минимальным объёмом кода. Тем же API доступен flash-call, если позже
понадобится удешевление — без переписывания интеграции.

## Дизайн

### 1. `SmscGateway` в `services/sms.py`

Новый класс рядом со `StubSmsGateway`, регистрируется в `get_gateway()` под
`SMS_GATEWAY=smsc`. Ветка `else: raise ValueError` сохраняется: опечатка в env
падает, а не притворяется стубом.

Конфигурация через env, добавить в `.env.example`:

- `SMSC_LOGIN`
- `SMSC_PASSWORD`
- `SMSC_SENDER` — зарегистрированное имя отправителя

Читаются при создании гейтвея. Отсутствие любого из трёх — `ValueError` при
инициализации, чтобы поломка конфига проявилась на старте, а не как 502 у
первого живого пользователя.

Транспорт — `httpx` (уже в `requirements.txt`, новых зависимостей нет).

Точные имена параметров и формат ответа SMSC сверяются по актуальной
документации провайдера на этапе реализации — по памяти не фиксируются.
Ошибка провайдера транслируется в исключение; роутер уже ловит его и отдаёт
502 с логом (`auth_phone.py:56-59`).

### 2. Отправка не должна блокировать event loop

Сейчас в `web/routers/auth_phone.py:56` синхронный вызов внутри `async def`:

```python
sms.get_gateway().send_code(phone, code)
```

Со `StubSmsGateway` это запись в dict — безобидно. С реальным провайдером это
сетевой запрос прямо в event loop.

Это тот же класс отказа, который 2026-07-20 уронил бота на 8+ часов
(коммит `8b02e6c`): зависший синхронный запрос к YooKassa заморозил Telegram
polling, apscheduler и весь HTTP-трафик, причём без исключения, которое мог бы
поймать watchdog.

Решение — то же, что уже применено в `services/payment_reconciler.py` и в фиксе
refill:

- явный socket timeout на httpx-клиенте;
- вызов через `asyncio.to_thread` в роутере.

Протокол `SmsGateway` остаётся синхронным; асинхронность живёт в роутере.

### 3. Антиабьюз — осознанно не делаем

`POST /api/auth/phone/request-code` не требует авторизации, а кулдаун в
`otp.issue` работает по ключу `(channel, destination, purpose)`, то есть **на
номер телефона**. При платных SMS это означает: ротация номеров расходует
баланс SMSC без какого-либо ограничения, а исчерпанный баланс ломает вход по
SMS для всех.

Риск озвучен и **принят владельцем проекта**. Лимиты по IP и суточный потолок
в этой итерации не реализуются; единственная защита — существующий кулдаун
60 секунд на номер. К вопросу возвращаемся по реальному трафику.

## Порядок выката

Код и включение UI смержить можно сразу, но на проде `SMS_GATEWAY` остаётся
`stub` до тех пор, пока не выполнены внешние шаги, от разработки не зависящие:

1. договор с SMSC.ru и пополнение баланса;
2. регистрация буквенного имени отправителя у операторов — процедура отдельная
   у каждого оператора и не мгновенная.

Только после этого `SMS_GATEWAY=smsc` на проде.

## Вне scope

- Flash-call верификация.
- Резервный провайдер и fallback-цепочка.
- Мониторинг баланса SMSC.
- Любые изменения в Telegram-OTP и email-логине.
