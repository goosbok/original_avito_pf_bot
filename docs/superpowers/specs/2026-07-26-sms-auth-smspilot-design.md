# SMS-авторизация: подключение реального провайдера (SMSPILOT)

**Дата:** 2026-07-26
**Провайдер:** SMSPILOT — решение владельца проекта. Ключевая причина выбора:
владелец действует как **физическое лицо без ИП/ООО**, а SMSPILOT — единственный
из проверенных провайдеров (SMSC, SMS.RU, TargetSMS), чья публичная оферта
явно допускает физлиц как клиентов. У SMS.RU и TargetSMS договор заключается
только с юрлицом или ИП.

## Ограничение статуса «физлицо» — определяет весь дизайн

Это не техническая деталь, а условие, без которого вход по SMS не заработает
в проде. Дословно из FAQ SMSPILOT:

- Частный клиент **без модерации** может слать SMS с любым текстом только на
  **белый список из 10 номеров**, каждый подтверждается кодом при добавлении.
- Чтобы слать **на любой номер**, текст сообщения должен совпадать с
  **сервисным шаблоном**, одобренным администратором SMSPILOT вручную.
  OTP-код подходит под их пример «проверочный код для подтверждения номера».
- Собственное буквенное имя отправителя — **только абонентам Билайн**,
  бесплатно. Для остальных операторов физлицу отдельное имя не полагается —
  общие рекламные имена тоже недоступны.
- Реклама запрещена; коды подтверждения разрешены только через одобренный
  шаблон.

Следствие для дизайна: параметр `from` **не задаём** — вместо своего имени
подставится то, что определит модерация вместе с одобрением шаблона.
Следствие для выката: до одобрения шаблона реальная доставка ограничена
десятью предварительно подтверждёнными номерами — это внешний блокер прода,
не часть кода (см. «Порядок выката»).

## Какой API используем

У SMSPILOT два API на общей авторизации (`apikey`):

- **API-1** (`https://smspilot.ru/api.php`, GET/POST) — одно сообщение за вызов.
- **API-2** (`https://smspilot.ru/api2.php`, POST) — пакетная отправка
  нескольких сообщений в одном запросе, с персонализацией каждого.

Наш `SmsGateway.send_code(phone, code)` шлёт по одному номеру за раз — пакетный
API-2 не даёт ничего сверх лишней вложенности JSON. Берём **API-1**.

## Дизайн

### 1. `SmspilotGateway` в `services/sms.py`

Новый класс рядом со `StubSmsGateway`, регистрируется в `get_gateway()` под
`SMS_GATEWAY=smspilot`. Ветка `else: raise ValueError` сохраняется: опечатка в
env падает, а не притворяется стубом.

Конфигурация через env, добавить в `.env.example`:

- `SMSPILOT_APIKEY` — единственный ключ авторизации (логин/пароль
  документация тоже поддерживает, но помечает как нерекомендуемый — используем
  apikey).

Читается при создании гейтвея. Отсутствие — `ValueError` при инициализации,
чтобы поломка конфига проявилась на старте, а не как 502 у первого живого
пользователя.

Транспорт — `httpx` (уже в `requirements.txt`, новых зависимостей нет).

**Контракт** (сверено по https://smspilot.ru/apikey.php 2026-07-26; запрос
живьём протестирован POST-запросом на реальный номер 2026-07-26 — см. ниже):

```
POST https://smspilot.ru/api.php
  apikey=<SMSPILOT_APIKEY>
  send=<текст с кодом>
  to=<phone без +>
  format=json
  charset=utf-8
  lang=ru
```

POST, а не GET: номер телефона и `apikey` не должны попадать в query string
(логи прокси, реферер и т.п.). API-1 поддерживает оба метода — выбираем POST.

`from` не передаём — см. раздел про ограничение физлица выше.

**Согласованный сервисный шаблон:** `"Code {код}"` (без двоеточия). Именно эта
формулировка одобрена модерацией SMSPILOT для номера-получателя — менять текст
после согласования нельзя без повторного одобрения.

Живой тест (`send=Code 111111`, `to=79521384051`, тестовый код 111111 вместо
реального OTP) подтвердил контракт:

```json
{"send":[{"server_id":"269435070","phone":"79521384051","price":"9.54",
          "status":"0"}],
 "balance":"2.66","cost":"9.54","server_packet_id":"269435070"}
```

Успех:
```json
{"send":[{"server_id":"9316849","phone":"79001234567","status":"0", ...}],
 "balance":"2935.50"}
```

Ошибка:
```json
{"error":{"code":"111","description":"Invalid phone",
          "description_ru":"Неправильный номер телефона"}}
```

В отличие от прежде рассмотренного TargetSMS, здесь **есть числовой
`error.code`** — не только текст. Ветвление на конкретные коды (например,
недостаточно средств, номер не в белом списке / шаблон не одобрен) делаем по
`code`, а не по подстроке в тексте.

Значимые детали, каждая из которых иначе всплывёт в проде:

- **Формат телефона — без `+`.** `normalize_phone` (`utils/phones.py`) отдаёт
  `+79001234567`, SMSPILOT ждёт `79001234567`. Ведущий `+` срезаем в гейтвее;
  сам `normalize_phone` не трогаем — от его формата зависят `otp.destination`
  и `identity`.
- **Ошибка приходит с HTTP 200.** Разбирать нужно тело: наличие ключа `error`,
  а не статус ответа.
- **`lang=ru`** — иначе тексты ошибок приходят по-английски; лог получаем
  на русском для читаемости при разборе инцидентов.
- **`ERROR 243 — LOOP PROTECTION`**: встроенная защита от повторной отправки
  дублирующихся сообщений, настраивается в личном кабинете. Нам это не должно
  мешать — код в каждом сообщении разный, текст не совпадает, — но при ручной
  отладке с фиксированным текстом легко на это напороться.
- **Текст SMS должен буквально совпадать с одобренным сервисным шаблоном**
  (пока не пройдена полная бизнес-верификация) — менять формулировку текста
  после одобрения нельзя без повторного согласования.

Ошибка провайдера транслируется в исключение; роутер уже ловит его и отдаёт
502 с логом (`auth_phone.py:56-59`).

### 2. Отправка не должна блокировать event loop

Сейчас в `web/routers/auth_phone.py:56` синхронный вызов внутри `async def`:

```python
sms.get_gateway().send_code(phone, code)
```

Со `StubSmsGateway` это запись в dict — безобидно. С реальным провайдером это
сетевой запрос прямо в event loop.

Это тот же класс отказа, который 2026-07-20 уронил бота на 8+ часов
(коммит `8b02e6c`): зависший синхронный запрос к YooKassa заморозил Telegram
polling, apscheduler и весь HTTP-трафик, причём без исключения, которое мог бы
поймать watchdog.

Решение — то же, что уже применено в `services/payment_reconciler.py` и в фиксе
refill:

- явный socket timeout на httpx-клиенте;
- вызов через `asyncio.to_thread` в роутере.

Протокол `SmsGateway` остаётся синхронным; асинхронность живёт в роутере.

### 3. Антиабьюз — осознанно не делаем

`POST /api/auth/phone/request-code` не требует авторизации, а кулдаун в
`otp.issue` работает по ключу `(channel, destination, purpose)`, то есть **на
номер телефона**. При платных SMS это означает: ротация номеров расходует
баланс без какого-либо ограничения, а исчерпанный баланс ломает вход по SMS
для всех.

Риск озвучен и **принят владельцем проекта**. Лимиты по IP и суточный потолок
в этой итерации не реализуются; единственная защита — существующий кулдаун
60 секунд на номер. К вопросу возвращаемся по реальному трафику.

Отдельно: пока действует белый список из 10 номеров (см. выше), абьюз с
произвольных номеров физически невозможен — сообщения на неодобренные номера
провайдер просто не доставит. Этот ограничитель исчезнет вместе с одобрением
сервисного шаблона, и тогда открытый риск станет реальным.

### 5. Тесты

Расширить `tests/unit/test_sms.py`:

- разбор успешного ответа (`{"send": [...], "balance": ...}`);
- **HTTP 200 с телом `{"error": {...}}` → исключение** (главный подводный
  камень: по статусу такой ответ неотличим от успеха);
- разбор `error.code` как числа, не только текста;
- телефон уходит без ведущего `+`;
- запрос уходит с `lang=ru` и без `from`;
- отсутствие `SMSPILOT_APIKEY` → `ValueError` при инициализации;
- `_reset_for_tests()` продолжает работать.

Отдельный тест: роутер не блокирует event loop — по образцу
`tests/unit/test_refill_yookassa_offload.py`.

Запуск через `docker exec`, не локальным python.

## Экономика и порядок выката

Код и включение UI смержить можно сразу, но на проде `SMS_GATEWAY` остаётся

Абонплаты и минимального платежа нет — чистая предоплата.

**Внешние шаги перед прод-запуском:**

1. ✅ Регистрация как частного клиента — сделано.
2. ✅ Сервисный шаблон `"Code {код}"` согласован модерацией SMSPILOT.
3. ✅ Живая отправка проверена 2026-07-26 на номере из белого списка
   (`+7 952 138 4051`) — SMS дошла, `status: 0`, см. пример ответа выше.
4. ⚠️ **Баланс почти исчерпан** (`2.66 ₽` после теста) — пополнить перед любым
   дальнейшим тестированием через реальный `services/otp.py`, иначе следующая
   отправка упадёт с ошибкой недостатка средств.
5. Пока не пройдена полная бизнес-верификация — доставка на произвольные
   номера может быть ограничена белым списком из 10 предподтверждённых
   номеров (добавляются в личном кабинете, каждый подтверждается кодом).
   Уточнить в личном кабинете SMSPILOT текущий статус верификации перед
   включением кнопки для всех пользователей в проде.
6. После пополнения баланса и снятия ограничения белого списка:
   `SMS_GATEWAY=smspilot` + `SMSPILOT_APIKEY` в env на проде.

## Вне scope

- API-2 (пакетная отправка) — не нужен при отправке по одному коду за раз.
- FLASHCALL, VOICE, 2WAY, HLR, PING — альтернативные каналы SMSPILOT,
  не рассматриваются в этой итерации.
- Апгрейд статуса до ИП/ООО и связанные с этим более широкие тарифы/имя
  отправителя — отдельное решение, не техническая задача.
- Резервный провайдер и fallback-цепочка.
- Мониторинг баланса.
- Любые изменения в Telegram-OTP и email-логине.
