# Админ-алерт на низкий баланс SMSPILOT

**Дата:** 2026-08-10

## Проблема

Регистрация на сайте сейчас идёт **только по SMS** (`SMS_GATEWAY=smspilot`).
Если баланс SMSPILOT закончится, никто не сможет зарегистрироваться — но
сейчас об этом не узнает никто, кроме как через ручной мониторинг или логи
контейнера. Нужен автоматический сигнал админам заранее (баланс низкий) и в
момент реального отказа (баланс кончился совсем, отправка упала).

## Не инцидент — превентивная фича

Найдено и подтверждено в ходе планового мониторинга прод-инфры 2026-08-09/10:
баланс SMSPILOT на тот момент был здоров (стабильно 977 ₽), но сам факт
отсутствия алертинга — реальный пробел.

## Архитектура

Проверка баланса — **не периодический пробник** (как `payment_probe.py` для
YooKassa), а **проверка в момент отправки SMS**. У SMSPILOT в ответе на
`send` уже приходит поле `balance` — читаем его без дополнительного запроса
к провайдеру, бесплатно и без лишней задержки.

Два независимых сигнала:

1. **Баланс низкий** — после каждой успешной отправки: если
   `balance < SMS_BALANCE_ALERT_THRESHOLD_RUB` — алерт админам. С кулдауном,
   иначе пока баланс не пополнят — алерт на каждую новую регистрацию.
2. **Отправка не удалась** — `SmspilotGateway.send_code` уже бросает
   исключение при ошибке провайдера (например баланс кончился совсем,
   `error.code=8` — недостаточно средств); `web/routers/auth_phone.py` уже
   ловит это и отдаёт юзеру 502. Сейчас на этом всё заканчивается — админы не
   узнают. Добавляем алерт в тот же `except`-блок, тоже с кулдауном (короче,
   чем у первого сигнала — это более срочный случай).

Канал — существующий `send_admins(msg, "errors")` (топик техподдержки в
Telegram), тот же, что уже использует `payment_probe.py`. Новой
инфраструктуры уведомлений не создаём.

## Реализация по файлам

### `services/sms.py`

`SmspilotGateway` получает атрибут `self.last_balance: float | None = None`,
инициализируемый в `__init__`. После каждого вызова `send_code` (и при
успехе, и при ошибке — если провайдер прислал `balance` в теле ответа) —
обновляем `self.last_balance`.

`SmsGateway` Protocol **не меняем** — баланс это специфика конкретного
провайдера (`StubSmsGateway` баланса не имеет), не общий контракт интерфейса.

### `web/routers/auth_phone.py`

После успешного `await asyncio.to_thread(gateway.send_code, phone, code)`:

```python
if isinstance(gateway, SmspilotGateway) and gateway.last_balance is not None:
    if gateway.last_balance < SMS_BALANCE_ALERT_THRESHOLD_RUB:
        await _maybe_alert_low_balance(gateway.last_balance)
```

`isinstance` вместо `getattr`-дак-тайпинга — явное решение специально для
этого провайдера, не скрытый общий контракт.

В существующем `except Exception:` (строка, где формируется 502) — перед
`raise HTTPException` добавляем `await _maybe_alert_send_failure(phone, exc)`.
Обе `_maybe_alert_*`-функции — best-effort, обёрнуты в свой `try/except`, как
в `payment_probe.py`: сбой отправки алерта никогда не должен уронить сам
эндпоинт или замаскировать исходную ошибку.

### Кулдауны — через таблицу `settings`

Тот же паттерн, что уже используют `get_setting`/`edit_setting` в
`auto_launch_export.py` («уже бегал сегодня»). Два независимых ключа:

- `sms_balance_alert_last_sent` — таймстемп последнего алерта «баланс низкий».
- `sms_send_failure_alert_last_sent` — таймстемп последнего алерта «отправка
  не удалась».

Перед отправкой алерта: если `now - last_sent < cooldown` — не слать, просто
залогировать на INFO, что подавили повтор. `get_setting`/`edit_setting` —
синхронные sqlite-вызовы, вызываются напрямую без `asyncio.to_thread` (как и
весь остальной синхронный sqlite-доступ в этом кодбейзе — это быстрые
локальные запросы, не сетевые вызовы, офлоадить незачем).

### Конфиг

`.env.example` + `data/config.py`, по образцу `WELCOME_BONUS_RUB` /
`PAYMENT_PROBE_INTERVAL_MIN`:

```
SMS_BALANCE_ALERT_THRESHOLD_RUB=200
SMS_BALANCE_ALERT_COOLDOWN_MIN=60
```

Оба сигнала используют одну и ту же переменную кулдауна (60 минут по
умолчанию) — разделять на два отдельных env var для двух похожих по смыслу
таймингов сочтено избыточным (YAGNI); независимость обеспечивают разные ключи
в `settings`, не разные конфиги.

## Текст алертов

Формат — по образцу `payment_probe.py` (HTML `parse_mode`, эмодзи-заголовок,
`<code>`/`<b>` разметка):

**Баланс низкий:**
```
⚠️ <b>Баланс SMSPILOT заканчивается</b>

Остаток: <code>187.50 ₽</code> (порог: 200 ₽)
Регистрация по SMS — единственный способ входа, скоро перестанет работать.
Пополнить: https://smspilot.ru/

Время: 2026-08-10 06:00:00
```

**Отправка не удалась:**
```
🚨 <b>Отправка SMS не работает</b>

Ошибка: <code>SMSPILOT error 8: Недостаточно средств</code>
Телефон: <code>+7999...1234</code> (регистрация не удалась, юзер получил 502)

Время: 2026-08-10 06:00:00
```

Номер телефона в алерте — с маскировкой середины (первые 4 и последние 4
символа нормализованного номера, остальное — `***`), чтобы не светить ПД
юзера в служебном чате целиком без необходимости. Пример: `+79991234567` →
`+799***4567`.

## Тесты

- `SmspilotGateway`: `last_balance` обновляется после успешного `send_code` и
  после ошибки (если провайдер прислал `balance`).
- Роутер: низкий баланс → `send_admins` вызван один раз, повторный вызов в
  пределах кулдауна → не вызван; после истечения кулдауна (замоканное время) →
  вызван снова.
- Роутер: `send_code` бросает → `send_admins` вызван с алертом о сбое,
  502 всё равно отдаётся юзеру (алерт не блокирует и не подменяет ответ).
- Сбой самого `send_admins` (замокать исключение) → эндпоинт всё равно
  отвечает штатно (502 или 200), не 500.

Запуск — `docker compose --profile test run --rm --build test pytest ... -v`.

## Вне scope

- Периодический пробник баланса (текущий подход — на события, этого
  достаточно при нынешнем трафике регистраций).
- Уведомление конкретно в `data.config.ADMINS` — этот список не используется
  нигде в проекте для реальной отправки, весь админ-алертинг идёт через
  `send_admins`/топик поддержки; заводить второй параллельный канал не нужно.
- Автоматическое отключение SMS-регистрации при пустом балансе (сейчас юзер
  просто получает 502 на каждую попытку) — отдельное решение, не в рамках
  этой задачи.
